# 政策立案ツール（チームみらい学生部・政策立案部門）

政策提言PJを、運用マニュアル（提言書型PJの進め方）どおりに進めるためのツールです。
本文はGoogleドキュメントで書き、このツールは **進行の管理・MTGと議事録の要点・（今後）ヒアリング申請・資料・課題の構造化** を担います。

- Cloudflare Workers + D1（SQLite）+ Discordログイン（希望PJアンケートと同じ構成）
- **データはすべてサーバー（D1）に保存**します。端末（localStorage）には、まだサーバーに届いていない議事録などの書きかけだけを一時的に置き、保存できたらすぐ消します（電源が落ちた・電波がないときに消えないように。3日で消える）
- 書き込みの権限チェックはすべてサーバー側（`src/api/common.js` の `requireEditor`）で行います

## できること（フェーズ1〜3）

| ロール | メンバー（閲覧・入力）／管理者（部門長＋`ADMIN_IDS`（副部門長）＋管理者メニューで追加した人。PJ決めの運営、全PJの編集・アーカイブ）／部門長（`HEAD_IDS`。常に管理者。ヒアリングの一次確認）／代表（`REP_IDS`。ヒアリングの最終確認） |
| 希望PJアンケートとの連動 | 「希望PJアンケートと連動」の募集回は、アンケートのDB（`SURVEY_DB`、読み取りのみ）から選択肢・投票（順位なしの希望は同率として数える）・締め切りを1分ごとに映す。投票と種の追加はアンケートで行い、ツールではリサーチメモ・開票結果・「正式なPJにする」を使う。アンケートで投票しただけの人も、メンバーの一覧に出る。**いまは連動を外している**（PJ決めはツールの中で行う。2026年秋の分は取り込み済み）。`SURVEY_DB` を設定すれば、また連動できる |
| 因果の樹形図（PJの「樹形図」タブ） | いちばん上に「課題」、その下に原因を枝分かれさせる（下の段が原因、上の段がその結果。画面に明記）。ノードは説明・数字による根拠・参考事例（国内／海外）・メモ・担当・出典（資料と紐づけ）を持つ。親の付け替え可（輪になる付け替えは不可）。同時編集は版番号で衝突を検知 |
| 施策（PJの「施策」タブ） | 樹形図の課題・原因に紐づけ、「どの課題から生じた施策か」をまとめて表示。型：現状・課題・参考事例・施策の内容（何をするか・導入フロー・予算感）・FAQ。Googleドキュメントに貼れる形でコピー |
| 資料（PJの「資料」タブ／「確認する」→ 資料） | タイトル・URL・種類・出典・日付・PJ（または部門共通）・要点メモ・登録者。「一次出典を確認済み」のチェックがない資料には ⚠ 未確認。PJ・種類・確認状態・キーワードで絞り込み。運用ルールを画面に常時表示 |
| 発表・提出（PJの「発表の準備・提出」タブ） | 発表日（未定なら仮）と準備状況の一覧。①発表準備：アブストラクト（提出状態・日付・URL）、アウトプット形式と発表資料のURL、役割分担（司会・スライド係・議事録係・スクショ係）、リハーサル（2週間前から複数回の目安を表示、見てもらう人・出た指摘、カレンダーにも表示）、発表資料の送付（前日までの期限）。②政調からのフィードバック：項目ごとに未対応／対応中／反映済み、担当・関係する施策・どう反映したか、反映の進み具合。③最終提出：期限（修正・最終提出の工程）、状態・提出日・改訂版URL。役割分担と発表資料は「発表する」画面にも出る |
| 発表する（ホーム） | PJの概要・メンバー・役割分担・発表資料・本文ドキュメント・発表時の注意点に加えて、**雑メモ**（自動保存。PJごとに1つ）と**フィードバックの追加**（「発表の準備・提出」タブの管理に未対応として入る）。この2つはログインしていれば誰でも使える |
| 管理者メニュー | 管理者だけに表示。管理者ができることの一覧、管理者の追加・削除、承認者と設定の状態、アーカイブしたPJ。人事（アーカイブ以外のPJごとの配属メンバーと工程、進行中のPJに入っていない人。「🔀 異動」ボタンを押すと出る欄で誰を・どこから・どこへを選んで異動、表の「×」で外す・「＋ 追加」で入れる。本人にお知らせ）と、ログイン状況（ログイン済みの人を最終ログイン順に、役割タグつきで。アンケートで投票しただけの未ログインの人、未ログインの部門長・代表も表示） |
| スマホ表示 | メニューは画面下のタブバー（アイコンつき）、タブは1行で横スクロール、工程の数直線は横スクロール（いまの工程に合わせて表示）、入力欄は16px。サイトはズームできない（ピンチ・ダブルタップ・入力時の自動拡大を止める） |
| 画面の考え方 | 途中のページ（ホーム・確認する・PJを選ぶだけのページ）は名前とボタンだけにし、説明や細かい情報は最後に開くページ（PJ・議事録・発表・定例など）に集める。PJを選ぶページは共通のPJ名リスト（参加中のPJを上に、ほかのPJは折りたたみ）。ルールの説明は申請フォームなど使う場所に置く |
| PJの始め方 | PJはPJ決めの種から始める（PJ一覧から直接は作れない）。管理者は「正式なPJにする」。だれでも、種のカードの「⋯」→「個人PJとして進める」で、普通のPJと同じように（メンバーを選んで）始められ、始めた人は必ずメンバーに入る。個人PJが始まると管理者全員にお知らせ。PJ一覧・PJ画面に「個人PJ」と出る |
| アーカイブ | PJ一覧の「アーカイブ」タブに、完了したPJと一時中止（アーカイブ）したPJを並べる。一時中止したPJは、PJメンバーと管理者が「PJ決めのアンケートに入れる」で受付中のPJ決めに種として戻せる（記録はPJに残り、その種をまたPJにするとき「前のPJを戻す」で記録ごと戻る） |
| PJ管理 | 名前・型（提言書型）・開始日・最終発表日・メンバー・Googleドキュメント4種類（リサーチドキュメント／課題共有の資料／政調用の本文／政調用の台本）のURL・MTGの進め方 |
| 工程の誘導 | 8工程（PJ決め→課題リサーチ→課題共有の資料作成・発表準備→政調での課題共有→施策考案→提言書作成・発表準備→最終発表→修正・最終提出）の進行バー、「いまここ」、工程ごとのチェックリスト（マニュアルから作成、PJ独自の項目も追加可） |
| 資料の送付 | 課題共有の資料・最終発表の資料・改訂版の送付は部門長が行うため、工程のチェック項目は「部門長をメンションして、〇〇をフォーラムに投稿する」。チェックが入ると部門長・副部門長に通知（お知らせ。Bot設定時はDMも） |
| MTG・議事録の置き場所 | PJの「工程」タブのいちばん上に「ミーティング」欄（MTGの追加・これからのMTG・定例の設定）。これまでのMTGの議事録は、開いた日が入る工程のカードに並ぶ |
| チェックと議事録 | チェックした項目は、その日のMTG（なければ直近1週間で議事録のあるMTG）に自動で結び付き、工程画面から議事録を開ける。「議事録を選ぶ」で選び直せる。議事録の画面でも、いまの工程のチェックを入れられる（そのMTGに結び付く） |
| PJの完了 | 「発表の準備・提出」タブで最終提出を「提出済み」にして保存すると（確認画面のあと）、部門長・副部門長に完了の承認を依頼するお知らせが届く（部門長・副部門長が保存したときも承認待ちになり、画面の「承認してPJを完了にする」で完了）。PJ画面の上に「承認待ち」と出て、部門長・副部門長が「承認してPJを完了にする」か「差し戻す」（理由つき）を選ぶ。最後の工程の「部門長に完了の承認を依頼する」からも依頼できる。完了したPJは「進行中に戻す」もできる。PJ一覧には「完了の承認待ち」と表示。「編集」の状態で完了にする・戻すのも部門長・副部門長だけ |
| お知らせが届く操作の確認 | 誰かにお知らせ（BotがあればDM）が届く操作は、押す前に確認画面を出し、誰に何が届くかを書く：MTGの追加・中止・中止の取り消し・臨時MTG、工程を進める、部門長に知らせるチェック項目、タスクの担当（自分以外）、議事録の保存・MTGを終える（「次回までにやること」の新しい担当・次回の日程。担当のお知らせは自動保存のたびではなく、このときにまとめて送る）、PJの作成・編集（メンバー追加・定例の変更）、フィードバックの追加、最終提出、完了の承認・差し戻し・進行中に戻す、人事の異動・追加・外す、ヒアリングの申請・再申請・承認・差し戻し・スレッド作成 |
| 工程の期限 | 開始日から自動計算。最終発表日が未定なら「8週目の終わり」を仮に置き、決まって入力すると「発表準備＝前日まで」「最終提出＝発表日＋4週間」に組み直す。手で変えた期限は組み直さない（「自動に戻す」で解除） |
| タスク | タイトル・担当・期限・状態（未着手／進行中／完了）・工程。期限はGoogleカレンダーに追加できる。完了したタスクは「完了したタスクも表示」で出し入れでき（PJのタスク・自分のタスク・カレンダーで共通。開いているあいだ続く） |
| MTG日程 | 定例：曜日（複数可＝週2回にも対応）・時刻・毎週／隔週。4週間先まで自動で入り、休みの回は「中止」にできる。毎回決める：議事録の最後に「次回のミーティング日程」欄（任意）があり、議事録と一緒に登録される |
| カレンダー | 部門の定例・MTG・リハーサル・タスクの期限・工程の期限を表示（部門の定例は「自分の予定」でも出る。定例の予定から出し、開いた定例があればその議事録へ）。表示は「月・週・3日・1日・スケジュール」をプルダウンで切り替え（最初はスマホならスケジュール、PCなら月）。週・3日・1日は時間軸（重なる予定は横に並べ、今の時刻に線）、月は日付を押すとその日の1日表示へ。予定を押すと詳細（日時・場所・PJ・議事録の有無／担当・状態など）が出て、MTGでは「議事録を見る」（読むだけで開く。「今回話し合うこと」だけはMTGの前に書いておける）と「MTGを始める」（過ぎたMTGは「議事録を書く」）を選べる。ほかはタスク・PJを開いたりGoogleカレンダーに追加したりできる（スマホでは下から出るシート）。「表示」ボタンの中で、自分の予定／部門全体・予定の種類（MTG・リハーサル・タスクの期限・工程の期限）ごとの表示／非表示・完了したタスクを切り替え（ボタンを増やさないよう1か所にまとめる）。スケジュール表示の各予定にGoogleカレンダー追加ボタン。定例MTGは繰り返し予定として追加でき、ICSもダウンロードできる |
| 議事録 | 前回の宿題（前回の「次回までにやること」を自動で引き継ぎ、完了チェック）／今回話し合うこと／概要／次回までにやること（担当・期限つきでタスクに登録）。「Notion用にコピー」でまとめて、各項目の「📋 コピー」で項目ごとにMarkdownをコピー。PJの「リサーチドキュメント」ドキュメントを「今回話し合うこと」と「概要」のあいだに埋め込み表示 |
| 同時編集 | PJのMTGの議事録は自動保存で、開いているほかのメンバーの画面に数秒で反映。欄ごとに書けるのは1人（「〇〇さんが入力中」）。定例の議事録・進捗共有は、同時に保存してぶつかったら相手の変更を取り込んで保存し直す（両方が同じ欄を変えていたら両方残す）。PJ・タスクなどは版番号で衝突を検知し、後から保存した人に「再読み込みしてください」と返す |
| 書きかけの保護 | 定例の議事録・進捗共有・事務連絡・PJの作成／編集・発表準備・ヒアリング申請は、保存していない内容があるまま別の画面へ移ろう・タブを閉じようとすると確認が出る |
| ホーム | 「ミーティングを始める」「確認する」「発表する」「定例」から選ぶ。今日のMTGの件数・お知らせの未読数・今日が定例の日ならその時刻を小さく表示。参加しているPJが1つだけなら「ミーティングを始める」でそのPJの選択肢を最初から開く |
| ミーティングを始める | まず「PJのMTG」「定例イベント」「その他のMTG」から選ぶ（PJ画面から来たときはPJのMTGへ直接）。**定例イベント**：ニュース勉強会・意見交換会を選び、どの定例の議事録に入れるか（最近終わった定例2回・今日の定例・予定から次の3回）を選ぶと、タイマーつきの議事録が開き、書いた内容はその定例の議事録の同じ名前の欄に入る（だれでも書ける。まだ始めていない定例なら書き置きになり、その定例を始めると議事録に移る。「MTGを終える」で、作ってある定例ならNotionの定例の議事録も書き直す）。**その他のMTG**（PJ・定例以外）：カテゴリー（いまは「その他」だけ。政策立案部門は選べない。あとで代表・副代表・企画部門・広報部門・デザイン部門などを足せる）→ プロジェクトを今あるものから選ぶか、新しく作る → タイマーつきの議事録。新しく作ったプロジェクトは、Notionの「その他」ページ（設定 NOTION_OTHER_PAGE）の「プロジェクト」欄（名前に「プロジェクト」が入ったデータベース。見つからなければページの中）にページができ、MTGの議事録はその中に1回ずつページとして入る（「保存する」「MTGを終える」のとき。2回目からは同じページを書き直す）。これまでの議事録は「確認する → その他のMTG」。管理者メニューの「Notionの「その他」ページにつながるか確かめる」で、インテグレーションが接続されているか確かめられる。**PJのMTG**：PJの「今からMTGを始める」→「予定していたMTGを始める」（今日以降の予定から選んで議事録を開く）か「臨時でMTGを始める」（日時・場所を確かめてから作成）を選ぶ |
| MTGの再開 | 「ミーティングを始める」でPJを選ぶと「↩ 前回の続き（再開）」が出る（この30日の過去のMTGから選んで、その議事録の続きを書く）。定例は、終えたあとでもその日のうちなら「↩ 定例を再開する」（管理者）で進行中に戻せる（終えたあとに書かれた進捗共有・事務連絡もまとめ直す） |
| タイマー | PJのMTGの議事録（書く画面）と進行中の定例は、開くと自動で経過時間を数える（定例は始めた時刻から）。発表する画面は、いちばん上（スクロールしても残る）に発表用のタイマー：発表の種類（政調MTG／その他の発表。目標時間の初期値が変わる）を選び、「発表スタート」→「発表終わり」でフィードバックの計測に切り替わり、「フィードバック終わり」で止まる。発表・フィードバックそれぞれ目標時間を選べて、残り時間／超過と、目標に近づくにつれ色（緑→青→赤→紫）が変わる。PJのMTGは始めた時刻をサーバーに記録するので、再読み込みしても、ほかのメンバーの画面でも同じ時間になる（4時間以上たって開き直すと始め直し） |
| 定例 → 進捗を書く | **どの定例に向けて書くかを毎回選ぶ**（最近終わった定例2回・今日の定例・予定から次の3回。定例の予定も記録もないときだけ、今までどおり「次の定例」）→ PJを選んで、定例で共有する進捗（前回の定例からやったこと・次の定例までにやること・困っていること）を記入。今日の定例が始まっていればその定例に、まだなら（または終わっていれば）次の定例に入る。選んだ定例がまだなら、その日に向けた書き置きになり、その定例を始めると議事録に移る（日を決めずに書いたものもあれば後ろに足して1つにする）。終わった定例を選んだときは、「保存する」でNotionの定例の議事録も書き直す。前回共有した内容も見られる。全体・項目ごとにNotion用にコピーできる。区切りは「定例を始める」「定例を終わる」：前の定例を終えてから次の定例を始めるまでに書いたものは次の定例へ、定例の最中に書いたものはその定例へ入る |
| 定例 | 全員が開ける入口。「定例の記録」（過去の定例の一覧 → 記録を見る。編集は管理者）、「進捗を書く」（PJを選んで直近の定例に向けた進捗を書く）。部門長・副部門長（管理者）には「事務連絡を書く」（予定から直近3回の日時を選んで、その定例の事務連絡を書き置き。「保存する」を押すと、まだ始めていない定例でもNotionの定例の議事録ページを作って入れる（定例を始めると、そのページを引き継ぐ）。定例を始めるとその日の議事録に移る。作成済みの定例なら直接書く）と「定例」（「定例を始める」＝予定から直近3回の日時を出し、押すとその日時の定例の議事録を作る／予定外で今日始めることもできる。「定例を予定する」＝毎週◯曜日の◯時を、期間を決めて登録）。定例の日付は朝6時で切り替える（夜の定例も日付をまたいで続く）。前もって作った先の定例は「準備中」と表示し、それまでに書かれた進捗共有はその定例に入る |
| 外部ヒアリング（記録） | 実施後の要点を、相手・目的とあわせてNotion用にコピーできる |
| 確認する | お知らせ（未読数）・自分のタスク・資料・外部ヒアリング（見られる人だけ）の入口だけを並べる（カレンダー・PJ・PJ決めは常に出ているメニューから） |

| 投票の秘密 | 誰が何に投票したか（各種の希望者・割り振り案・投票者ごとの希望順）は、部門長・副部門長（管理者）だけが見られる。ほかの人には希望の人数だけを出す |
| PJ決めのコメント | 種のカードの「💬 コメント」を押すとコメント欄が開き、誰でも書ける（件数をボタンに表示。消せるのは書いた本人と管理者） |

| 議事録を探す | 「確認する → 議事録を探す」（PJ画面のミーティング欄からも）。開くと最近の記録を新しい順に表示。PJのMTGの議事録（今回話し合うこと・概要・次回までにやること）・定例の記録（事務連絡・メモ・各PJの進捗共有）・発表の記録（メモ）を、言葉（空白で区切るとすべて含むもの）・PJ・期間（今日／昨日／今週／先週／今月／先月、または日付を指定）で探す。種類は件数つきのボタンで切り替え。結果は日付を大きく出し、見つかった言葉に印を付けた前後と「全文を見る」、「開く」でその記録へ。条件は画面のURLに残る |
| お知らせ・通知 | 「確認する → お知らせ」に、タスクの担当になった・MTGが入った／変わった／中止・PJのメンバーになった・工程が進んだ・フィードバックが追加された・ヒアリングの確認依頼や結果を表示。PJのお知らせはそのPJのメンバーだけに届き、操作した本人にも届く（自分でタスクの担当になった・MTGを入れた、なども残る）。Bot設定時は、タスクの担当・MTGの追加／変更／中止・ヒアリング・リマインドをDMでも送る（メンバー追加・工程・フィードバックはお知らせだけ） |
| 自分のタスク | 自分が担当のタスクを全PJからまとめて表示・完了にできる（担当者はPJメンバーでなくても状態を変えられる）。上の欄から自分のタスクを追加できる（参加中の進行中のPJを選ぶ。管理者はすべての進行中のPJ。担当は自分、工程はそのPJのいまの工程） |
| PJ一覧の進み具合 | 各PJのカードに、PJ画面の上部と同じ工程の数直線（済んだ工程は✓、いまの工程を強調、各工程の期限） |

## ローカルで動かす

```bash
npm install
cp .dev.vars.example .dev.vars
npm run db:migrate:local
npm run dev
```

http://localhost:8787 を開くと「ローカル確認用ログイン」が出ます（`.dev.vars` の `DEV_LOGIN=true` かつ localhost のときだけ）。
名前を「部門長」にすると部門長、「代表」にすると代表の権限で入れます（`.dev.vars` の `HEAD_IDS=dev-部門長` などによる）。

テスト（工程の期限計算・定例MTGの日付計算）：

```bash
npm test
```

画面を実際に動かす自動テスト（Playwright。アクションボードと同じ道具）：

```bash
npm run test:e2e
```

テスト用の空のデータベース（`.wrangler/e2e`）でローカルのサーバーを立ち上げ、ローカル確認用ログインで「PJを作る → MTGを始める → 議事録を書く → MTGを終える → 記録・検索・タイムラインに出る」などを通しで確かめる（`e2e/`）。初めてのときは `npx playwright install chromium` が必要。GitHub に push するたび、GitHub Actions（`.github/workflows/test.yml`）で両方のテストが自動で動く。

### エラーの監視

サーバーと画面で起きた想定外のエラーは、D1 の `error_logs` に記録され、管理者メニューの「⚠️ エラーの記録」で見られる（最新500件）。シークレット `SENTRY_DSN` を入れると、Sentry（アクションボードと同じ監視サービス）にも送る：

```bash
npx wrangler secret put SENTRY_DSN
```


## 本番にデプロイする

作業はすべて、このフォルダ（`policy-planning-tool`）で行います。順番が大事です（URLが決まってから、そのURLをDiscordに登録するため）。

1. **Cloudflareにログインしているか確認**
   ```bash
   npx wrangler whoami
   ```
   本番を置くアカウントが出ればOK。出なければ `npx wrangler login`。`wrangler.toml` の `account_id` で、本番とテスト版を別のアカウントに置ける。
   - 外部ツールのログインを受け付けないアカウント（組織のアカウントなど）では、ダッシュボードの「My Profile → API Tokens」で「Edit Cloudflare Workers」＋「D1 Edit」のトークンを作り、このフォルダの `.env` に `CLOUDFLARE_API_TOKEN=...` と書く（`.env` はGitHubに入らない）
2. **本番用のDBを作る**（最初の1回だけ）
   ```bash
   npx wrangler d1 create policy-planning
   ```
   出力の `database_id = "…"` を、`wrangler.toml` の `database_id` に貼り替える。
3. **`wrangler.toml` の `[vars]` を埋める**（Discordの「設定 → 詳細設定 → 開発者モード」をオンにして、右クリック →「IDをコピー」）
   - `DEPT_ROLE_ID`：政策立案部門のロールID（サーバー設定 → ロール → 右クリック）。ログインには不要で、外部ヒアリングを見られる人の判定に使う
   - `HEAD_IDS`：部門長のユーザーID　／　`REP_IDS`：代表のユーザーID　／　`ADMIN_IDS`：部門長のほかに常に管理者にする人（副部門長など）
4. **本番DBにテーブルを作る**
   ```bash
   npm run db:migrate:remote
   ```
5. **デプロイ**（ここで初めてURLが決まる）
   ```bash
   npm run deploy
   ```
   最後に出る `https://policy-planning.〇〇.workers.dev` が公開URL。この時点ではまだログインできない（`?error=config` になる）。
6. **Discordのログイン用アプリを作る**：https://discord.com/developers/applications → New Application（名前は「政策立案ツール」など）
   - 左の「OAuth2」→ Redirects に `https://policy-planning.〇〇.workers.dev/auth/callback` を追加して保存
   - 同じ画面の Client ID をコピー、「Reset Secret」で Client Secret を出してコピー（Secretは一度しか表示されない）
   - 希望PJアンケートのアプリを流用してもよいが、Secretを作り直すとアンケート側も設定し直しになるので、新しく作る方が安全
7. **シークレットを入れる**（コマンドを打つと値を聞かれるので貼り付ける。画面にもgitにも残らない）
   ```bash
   npx wrangler secret put DISCORD_CLIENT_ID
   npx wrangler secret put DISCORD_CLIENT_SECRET
   npx wrangler secret put SESSION_SECRET
   ```
   `SESSION_SECRET` に貼る値は、次のコマンドで作ったランダムな文字列：
   ```bash
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```
   シークレットは入れた瞬間に反映される（デプロイし直さなくてよい）。
8. **動作確認**：公開URLを開いて「Discordでログイン」→ 部門長・代表の名前の横にバッジが出るか確認。
9. **アクションボードの「その他」に公開URLをリンクとして追加**

### テスト版（みんなで試す用）

本番とは別のURL・別のDBで動く。画面上部に「テスト版」の帯が出る。毎朝のリマインドと渉外フォーラムへのスレッド作成はしない。

- URL：https://policy-planning-test.〇〇.workers.dev
- 更新：`npx wrangler d1 migrations apply policy-planning-test --remote --env test` → `npx wrangler deploy --env test`
- 最初に1回だけ：Discordの開発者ポータル（OAuth2 → Redirects）に `https://policy-planning-test.〇〇.workers.dev/auth/callback` を追加し、`npx wrangler secret put DISCORD_CLIENT_SECRET --env test` でClient Secretを入れる

### ヒアリング申請の通知とスレッド作成を有効にする（フェーズ1b）

1. **Botのトークン**（アクションボードのBot）をシークレットに入れる
   ```bash
   npx wrangler secret put DISCORD_BOT_TOKEN
   ```
2. **`wrangler.toml` の `HEARING_FORUM_ID`** に渉外フォーラムのチャンネルIDを入れる（フォーラムで「タグ必須」なら `HEARING_FORUM_TAG_ID` も）
3. Botに渉外フォーラムで「チャンネルを見る」「メッセージを送信」「投稿の作成（公開スレッドの作成）」「スレッドでメッセージを送信」の権限があることを確認
4. `npm run deploy`

未設定のあいだも申請・承認はでき、DMとスレッド作成だけが止まります（ヒアリング画面に注意が出ます）。

### うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| ログイン後 `?error=config` | `DISCORD_CLIENT_ID` / `DISCORD_CLIENT_SECRET` が未設定か間違い → 手順7をやり直す |
| Discordの画面で「Invalid OAuth2 redirect_uri」 | 手順6の Redirects のURLが公開URLと1文字でも違う（`https`、末尾の `/auth/callback`） |
| `?error=guild` | 学生チームのサーバーに入っていないDiscordアカウントでログインした |
| 画面に「サーバーでエラー」 | `npx wrangler tail` を実行したまま操作すると、エラーの内容が見られる |

### 2回目以降の更新

```bash
npm run db:migrate:remote   # migrations/ に新しいファイルが増えたときだけ
npm run deploy
```
`wrangler.toml` の `[vars]`（部門長・代表のIDなど）を変えたときも `npm run deploy` で反映される。データは消えない。

## 画面のつながり（考え方）

- **PJ画面がすべての作業の拠点**：上に「▶ MTGを始める」「🎤 発表する」「📝 定例の進捗を書く」が並ぶ。ホームの4択は、そこへの近道
- **言葉**：「議事録」はPJのMTGの記録だけ。定例でPJが書くものは「進捗」、定例そのものの記録は「定例の記録」。発表は「発表する」（本番：タイマー・記録）と、PJの「発表の準備・提出」タブ（準備・フィードバックの反映・最終提出）。両方の画面の上に、もう片方へのリンクがある
- **お知らせ**：画面の上の🔔（未読数つき）を押すと、その場に小さな枠で新しい8件が出る（ページは移らない。開くと既読）。押すとその画面へ。枠の下から「すべて見る」「自分のタスク」へ
- **メニュー（下のバー／PCでは上）**：ホーム・自分のPJ・タイムライン・カレンダーの4つ。PJ決めは「自分のPJ」のいちばん上（受付中なら目立たせる）、管理者メニューはホームの4択の下から
- **タイムライン**：部門で起きたこと（PJの始まり・工程の完了・議事録・定例の進捗・発表・PJの完了・政策の種・定例の終わり）を、この30日分新しい順に。「部門全体／自分のPJ」で切り替え。押すとその画面へ
- **達成感の演出**：チェックを入れると「ぽん」と動く。工程のチェックがすべて済んだとき・工程を進めたとき・PJが完了したときに紙吹雪（動きを減らす設定の人には出さない）
- **工程の数直線の進み具合**：いまの工程から次の工程への線が、いまの工程のチェックが済んだ分だけ伸びる
- **MTGを終えたときの進み具合**：PJ画面に戻るときは、数直線の線が「MTGの前 → 後」へ伸び、いまの工程の丸が弾む（「このMTGで◯項目進みました！」）。ホーム・カレンダーに戻るときは、進み具合の棒が伸び、このMTGで済んだ項目に順にチェックが入る画面を出す
- **タブの切り替え**：PJ画面などのタブを切り替えても、スクロールが上に戻らない（タブの列が同じ位置に残る）
- **PJの「記録」タブ**：このPJのMTGの議事録・定例の進捗共有・発表の記録を、月ごとに日付順で（種類は件数つきで切り替え、全文も見られる）
- **終わったあとの行き先**：「MTGを終える」は、始めた画面に戻る（ホームから始めたらホーム、カレンダーからならカレンダー、PJ画面からならPJ画面）
- **メニューの現在地**：MTGを始める・発表する・進捗を書く・外部ヒアリングはPJの作業として「PJ」が光る。ブラウザのタブには画面の名前を出す
- **横のリンク**：議事録 → このPJの定例の進捗を書く、進捗 → PJ画面、発表する → PJ画面・準備と提出、PJ画面 → 元になったPJ決め
